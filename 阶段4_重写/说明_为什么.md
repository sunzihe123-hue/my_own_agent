## 二、三个文件（为什么是三个，不是一个）

| 文件 | 角色 | 放什么 | 为什么不塞进测试文件 |
|---|---|---|---|
| `support.py` | 测试基础设施（support = 支撑） | 基类、假客户端、固定数据、日志重定向 | 两个测试文件都要用；写两遍就会有两份"慢慢不一致"的假客户端 |
| `test_tools.py` | 对 `tools.py` 的独立验收 | 4 条：schema 必填/类型/描述、execute 返回字符串、默认值 | 一个测试文件只对一个"被测对象"负责，红了立刻知道是哪块坏了 |
| `test_agent_log.py` | 对 `agent.py` 日志的验收 | 2 条：调用日志、结果日志 | 日志测试需要临时目录 + 日志重定向，和纯 schema 测试代价不同，分开跑更快 |

还有一个"破例"要解释：`support.py` 用 `sys.path.insert` 引入了 `阶段3_重写`。

- 规矩本来是"每个阶段目录自包含，不跨目录 import"；
- 但**测试层天然是横切的**（cross-cutting）：它是"验收者"，不该把被测代码再抄一份 —— 抄一份就变成"验证抄件"，真代码坏了你也发现不了；
- 中文目录名不能当 Python 包 import，只能 `sys.path.insert`（见 `交接文档.md` §6）。

## 三、写作顺序（每步都跑一次测试，看绿数）

| 步 | 写什么 | 写完的绿数 | 卡住时回看 |
|---|---|---|---|
| 1 | `support.build_registry`（fixture = 固定数据） | 0/6（数据就位，还没有测试） | 阶段 3 的 `test_tools.py` |
| 2 | `test_tools.py` 四条断言（一条一条填） | 1/6 → 4/6 | 阶段 3 的同名测试 |
| 3 | `support.TmpDirTest` + `FakeToolClient` | 4/6（给日志测试备料） | C 的构造/析构；阶段 1 的 `StoreTest` |
| 4 | `support.capture_logs` + `agent.py` 三处日志 | 4/6（观测手段就位，还没测） | 本节 §4.5 / §4.6 |
| 5 | `test_agent_log.py` 两条断言 | 5/6 → 6/6 | 本节 §4.7 |

> 顺序背后的依赖关系：**数据（fixture）→ 被测行为 → 观测手段 → 观测断言**。
> 基类（`TmpDirTest`）必须排在"用到它的子类测试"之前，但不必排第一 —— 让第一份反馈尽早到来。
> 反馈慢一点没关系，顺序反了会连着错好几次（比如先写日志测试，才发现 `capture_logs` 没写对，报错会指向测试而不是工具）。

## 四、每个部件为什么存在（回答"删了它会怎样"）

### 4.1 为什么测试是"第二份代码"

测试本身也会错，而且**错得更危险**：代码错，测试会红；测试错，你会去"改对的代码迁就错的断言"。
所以规矩是：测试先在**已知正确**的实现上跑绿，再拿去验收。

- 阶段 1~3 是教练先写好测试、你在实现上跑绿；
- 阶段 4 反过来：你在实现上**写**测试。所以判卷不是"跑绿就行"，而是"改坏实现，测试必须红"（§4.8）。

### 4.2 为什么要 `TmpDirTest`：每个测试一个干净起点

日志测试要往文件里写。如果写进项目目录：

1. 会留垃圾（下次 `git status` 一片红）；
2. 测试之间会互相污染（上一个测试的日志还在文件里，断言 `assertIn` 全绿——假绿）；
3. 可能盖掉真实数据。

`setUp` 每个测试前跑一次，`tearDown` 每个测试后跑一次（哪怕测试失败也会跑）。
用 `tempfile.TemporaryDirectory()` 建目录、`cleanup()` 删目录 —— 等于给每个测试发一张白纸，用完回收。

**C 类比**：`setUp` ≈ 构造函数（准备环境），`tearDown` ≈ 析构函数（释放资源）。

### 4.3 为什么 `FakeToolClient` 必须长得像真 SDK

`Agent` 的代码是按真 SDK 的形状写的：

```
client.chat.completions.create(model=..., messages=..., tools=...)
     └→ resp.choices[0].message   （message 上有 .content 和 .tool_calls）
```

替身如果长得不像（比如叫 `client.generate()`），那测的就不是真代码，而是"你为替身改出来的另一份代码"。
**插头形状必须一致**（duck typing，鸭子类型：只要"看起来像、能叫出声"就能当鸭子）。

这也是为什么项目里 `FakeClient` 用 `SimpleNamespace` 一层层套出 `.chat.completions.create`：
不是炫技，是为了让被测代码**一行都不用改**。

`FakeToolClient` 多记一个 `self.calls`：每次请求都存一份 `model / messages / tools`，之后可以断言"第二次请求时，模型看到了工具结果"。

> 注意 `[dict(m) for m in messages]`：**复制**一份再存。不复制的话，之后 `agent.messages` 被修改，你记录的那份也跟着变，断言就失去意义。

### 4.4 为什么日志不用 `print`

| | `print` | `logging` |
|---|---|---|
| 谁来写 | 每一处手写 | 模块级 `log = logging.getLogger(__name__)` |
| 能不能关 | 删代码 | `setLevel(WARNING)` 一句话过滤 |
| 有没有出处 | 没有 | 每条自带模块名、级别、时间 |
| 异常怎么记 | 只能打印 `str(e)`，没有栈 | `log.exception()` 自动带完整调用栈（traceback） |
| 往哪写 | 只能往屏幕 | `Handler` 决定：屏幕 / 文件 / 网络 / 内存 |
| **能不能被测试** | 不能（拦 `print` 很脏） | **能**（换 Handler 就能抓，见 §4.5） |

`log.exception()` 和 `log.error()` 的区别就一条：**exception 会带栈**。
报错时你最想知道"哪一行炸的、谁调它上来的"，只有 `log.exception` 给得了。

### 4.5 为什么日志能被测试：`Handler` 就是"出口"

`logging` 的结构是三级：

```
代码里的 log.info(...)  →  日志器 Logger  →（冒泡 propagate）→  根日志器 root  →  Handler（真正写出去的）→  文件/屏幕
```

- 日志默认最后落到 root 的 Handler 上（通常是 stderr）；
- `capture_logs.__enter__` 往 root **临时**挂一个 `FileHandler`（写进临时目录的 `.log` 文件）；
- 业务代码一行不改，日志就全进了文件；
- 测试读文件、断言内容 —— 日志从"给人看"变成"给测试看"。

所以 `capture_logs` 是**观测工具**：它不改变行为，只改变"日志去哪"。

### 4.6 为什么 `capture_logs` 必须"恢复现场"

三个必须：

1. `__exit__` 里 `removeHandler`：不摘掉，后面的测试会把日志继续写进你这个已关闭的文件（报错 / 串味）；
2. `__exit__` 里 `handler.close()`：`FileHandler` 有缓冲区，不 close 可能最后几行没落盘，你读到的文件是少的（本阶段最大的坑）；
3. `__exit__` 里恢复 root 的 level：不恢复的话，整个进程的日志级别被你永久改了，后面的测试全受影响。

`with` 保证 `__exit__` 一定执行——即使 with 块里抛异常。**手动删做不到这点**，这正是上下文管理器（context manager）存在的理由。

**C 类比**：RAII —— 资源在构造时申请、析构时释放，异常也不会漏。

### 4.7 为什么断言要"能区分"

看两条断言的强弱：

```python
self.assertIn("add", text)          # 弱：工具名记了就算过
self.assertIn('{"a": 2, "b": 3}', text)   # 强：参数也得记
```

判卷时"把参数从日志里删掉"，第一条测试**照样绿**——这是假绿。弱断言不会让程序出错，只会让你以为"有测试保护"。

同理，工具结果那条测试断言 `"5"`，是因为剧本里参数是 `{"a": 2, "b": 3}`、回答是 "都算完了"——**"5"只可能出现在结果日志里**。
如果回答写成 "2+3=5"，这条断言就失去区分力了。

> 判据：**这条断言，在哪种 bug 下会变红？** 想不出来，就说明它太弱。

### 4.8 判卷是什么（mutation testing，变异测试）

流程：把实现**故意改坏** 2~3 处（一次一处），跑测试，看**对应的**测试有没有变红。

- 红了 → 测试抓住了这个 bug（有效）
- 还是绿 → 测试没覆盖到，或者断言太弱（无效）

它证明的是"测试的质量"，而不是"实现的质量"。改坏后要能恢复，所以判卷必须在**可回退**的状态做（比如 `git diff` 或提前备份）。

本阶段的判卷清单在 `结构总览.md` §八，改坏点和"该红的测试"一一对应。

### 4.9 为什么三处日志放在这些位置

| 位置 | 记什么 | 事后能回答什么 |
|---|---|---|
| `chat()` 每轮开头 | 第几轮 + 历史条数 | "模型当时看到的是多长的对话"（越聊越傻 / 上下文爆了没） |
| 工具执行前 | 工具名 + 参数原文 | "模型到底要什么、给了什么参数" |
| 工具执行后 | 工具名 + 结果 | "工具是没跑、还是跑错了"（只有参数没有结果，没法分清） |
| `_call_model()` 异常分支 | `log.exception` | "这次请求为什么失败、哪一行炸的" |

没有这些日志时，一次失败的对话只能看到"用户说 agent 胡说"，三者不可区分：**模型没理解 / 工具没执行 / 结果没回填**。
三处日志正好把这三段切开。

### 4.10 为什么 `log.exception` 之后必须 `raise`

```python
except Exception:
    log.exception("调用模型失败")
    raise            # ← 绝不能省
```

- 日志是**记录**，不是**处理**；
- 吞掉异常（只 log 不 raise），上层会以为请求成功了，于是拿到 `None` 继续往下跑，最后在一个毫不相关的地方崩——更难查；
- 正确姿势："记下来，然后原样抛出去"，让调用方决定怎么办。

## 五、六个坑（都是本阶段真实会踩的）

1. **读了空文件**：没 `handler.close()`，缓冲区里的日志还没落盘。
2. **日志抓不到**：把日志写到了 root 之外且 `propagate = False` 的日志器上；或者 level 设成 `WARNING` 而代码用的是 `info`。
3. **测试互相污染**：没恢复 root level / 没摘 handler，第二个测试的断言被第一个测试的日志喂饱（假绿）。
4. **`sys.path` 写相对路径**：`sys.path.insert(0, "阶段3_重写")` 是相对**当前工作目录**的，PyCharm 右键 Run 的 cwd 一换就崩；要用 `Path(__file__).resolve()` 算绝对路径。
5. **编码**：`FileHandler` 不写 `encoding="utf-8"`，中文日志在 Windows 上按 GBK 写，读出来是乱码（断言当然全红）。
6. **断言太松**：见 §4.7，"日志里有 add"挡不住"参数没记"。

## 六、C 程序员对照表

| C 里 | 阶段 4 里 |
|---|---|
| `assert(x == 5)`（宏，失败就崩） | `self.assertEqual(x, "5")`（失败只算一条红，其余测试继续跑） |
| 构造函数 / 析构函数 | `setUp` / `tearDown`（每个测试一对） |
| `fopen` + `fprintf` | `FileHandler` + `log.info` |
| `freopen(..., stderr)` 重定向 | 换 Handler（`capture_logs`） |
| 带 backtrace 的 `fprintf(stderr, ...)` | `log.exception(...)` |
| `extern` 声明的头文件 | `import` + `sys.path` |
| 结构体指针强转成"相同前缀" | duck typing / `SimpleNamespace` 造替身 |
