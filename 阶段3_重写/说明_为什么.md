## 四、每个部件为什么存在

### 4.1 模型"会说话"却"不会做事"——工具调用是三件事

```
我们：把工具清单（名字 + 描述 + 参数）告诉模型      ← schemas()
模型：回一句"请帮我调用 add，参数是 {"a":2,"b":3}"  ← tool_calls
我们：真的执行 add(2, 3)，把结果发回去             ← execute()
```

缺任何一环都不通：不给清单模型不知道有什么；不执行等于它只会许愿；不回填它就不知道结果。

### 4.2 为什么用注册表，而不是 `if name == "add": ...`

```python
# 能跑但会烂掉
if name == "add":
    return add(**args)
elif name == "hello":
    return hello(**args)
elif ...
```

- 加一个工具 = 改三处（if 链、schema 清单、说明文档），漏一处就不一致
- 注册表是**数据驱动**：`self.tools` 是"名字 → 函数"的表，加工具 = 写函数 + 加装饰器
- C 类比：这就是 **dispatch table（函数指针表）**，比一长串 `switch` 好维护

### 4.3 为什么用装饰器自动生成 schema

手写 JSON Schema 长这样，一个参数就要 5 行，还容易和函数签名对不上：

```python
{"type": "object",
 "properties": {"a": {"type": "integer"}, "b": {"type": "integer"}},
 "required": ["a", "b"]}
```

而函数的签名里**本来就有**这些信息（参数名、类型、默认值）。`inspect.signature(func)` 读参数和默认值，`typing.get_type_hints(func)` 读类型标注，组合起来就自动生成了。

> 教训：**能从一个来源推导出来的东西，不要手写第二份**——两份迟早不一致。

### 4.4 为什么 schema 是 JSON

因为这是**给模型看的说明书**，而模型只能读文本。OpenAI 兼容接口的 `tools=` 参数规定就是这个 JSON 形状（`{"type": "function", "function": {...}}`），换成别的格式它不认识。

### 4.5 为什么 `execute()` 要把异常变成字符串

模型给错参数**非常常见**（它是概率模型，不是编译器）。如果把异常抛出去：

- 整个对话中断，用户看到 Python traceback
- 模型永远不知道自己错了，也就没有改正的机会

正确做法是：把错误当作**工具结果**交给模型——

```python
"错误：参数不匹配（add() got an unexpected keyword argument 'x'）"
```

模型看到这句，通常会自己改正参数再试一次。这就是"错误信息是产品的一部分"在 agent 里的版本。

### 4.6 为什么工具结果一律转字符串

模型只能读文本。`add(2,3)` 返回 `5`（int），直接塞进 `content` 位置会不符合接口要求，所以统一 `json.dumps`：`5 → "5"`，`{"a": [1,2]} → "{\"a\": [1, 2]}"`。`ensure_ascii=False` 是为了让中文不变成 `\u4f60\u597d`。

### 4.7 为什么 agent 是一个循环

一次工具调用往往不够。用户问"我下周有什么作业"，模型可能先调 `get_current_time` 才知道"下周"是哪几天，再调 `list_tasks`——两步之间有依赖，必须**看着第一步的结果**决定第二步。

所以：**调用模型 → 有 tool_calls 就执行 → 把结果放回对话 → 再调用模型**，直到它不再要工具为止。

### 4.8 为什么 assistant 的 tool_calls 要原样记进历史

这一步漏了，接口会直接报错（`tool` 消息找不到对应的 `tool_call`），或者模型反复重复同一个调用。因为对话历史是**模型判断下一步的唯一依据**：

```
assistant: 我要调用 add（id=call_1）
tool:      5（对应 call_1）
```

少了第一行，第二行就成了没有来由的悬空数据。

### 4.9 为什么 `role="tool"` 要带 `tool_call_id`

一次模型回复可能同时要调 3 个工具。结果回来时，得让模型知道"这个 5 是哪个调用产生的"。`tool_call_id` 就是这次调用的**唯一编号**，相当于回信时写清楚"回复你第 2 个问题"。

### 4.10 为什么要有 `max_steps`

模型可能陷入"调工具 → 看结果 → 再调同一个工具"的死循环（尤其是假客户端或工具总是报错时）。没有上限就是**无限烧钱 + 程序卡死**。上限到了就给它一句"步数太多，请把问题说具体点"。

### 4.11 为什么 system prompt 要写"必须调工具、不要编造"

模型很擅长**编**（幻觉，hallucination）：问它"我明天有什么作业"，它可能直接编一个。system prompt 是唯一能持续约束它的地方（每次请求都在最前面）。规则写清楚：要事实 → 先调工具；相对日期 → 先取当前时间。

## 五、五个坑

1. **`tool()` 忘了 `return func`** → 被装饰的函数变成 `None`，模块直接崩（测试 `test_decorator_returns_original_function` 专抓）
2. **`required` 把所有参数都塞进去** → 有默认值的参数变成必填，模型少传一个就报错（`test_param_with_default_is_not_required`）
3. **`execute()` 把异常抛出去** → 一条错误参数就让整个对话崩掉（`test_wrong_arguments_return_error_string` 等专抓）
4. **assistant 的 tool_calls 没记进历史** → 接口 400（`test_assistant_tool_calls_are_recorded`）
5. **`chat()` 里忘了 `content or ""`** → 模型只给 tool_calls 时 `content` 是 `None`，`None` 塞进消息里某些接口会报错

## 六、C 程序员对照表

| Python / 本阶段 | C 里对应什么 | 差别 |
|---|---|---|
| `ToolRegistry.tools` 字典 | `struct { char *name; fn_ptr; } table[]` | 字典按名字查，不用遍历 |
| `@reg.tool(...)` 装饰器 | 宏 + 自动注册 | Python 在函数定义时自动执行 |
| `inspect.signature` | 没有等价物 | Python 能在运行时反射函数签名 |
| `tool_calls` 列表 | 回调请求列表 | 由模型生成，不是程序写的 |
| `execute` 返回错误字符串 | `return -1` + 错误码表 | 错误是给模型读的自然语言 |
| `max_steps` | 循环计数器 + 超时保护 | 一样，防死循环 |
